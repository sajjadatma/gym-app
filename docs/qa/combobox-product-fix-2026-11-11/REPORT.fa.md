# اصلاح محصولی combobox و روشن‌سازی حفظ داده

تاریخ: ۱۱ نوامبر ۲۰۲۶، ۲۰ آبان ۱۴۰۵ — Asia/Tehran  
برنچ: `codex/finance-sandbox-v2`؛ تغییرات قبلی OpenCode حفظ شده‌اند.

## تغییر رابط

مشکل باز و بلافاصله بسته‌شدن لیست با کلیک در build تولیدی بازتولید شد. لاگ قبل از اصلاح، دو شکست در کلیک موبایل را نشان می‌دهد. ردیابی production با stack خوانا نشان داد `useOverlayPosition → onScroll → close` عامل بستن popup پس از بازشدن است؛ بنابراین توضیح قبلی که مشکل را صرفاً readiness تست می‌دانست کامل نبود.

در `frontend/src/components/M3.tsx`:

- بازکردن ورودی با کلیک صریح و touchend انجام می‌شود؛ لمس دیگر به compatibility click وابسته نیست.
- فوکوس ناشی از pointer با `preventScroll` گرفته می‌شود تا جابه‌جایی ناخواستهٔ viewport کمتر شود.
- popup پس از frame مربوط به بازکردن mount می‌شود؛ scroll فوکوس در همان رخداد، آن را بلافاصله dismiss نمی‌کند. زمان انتظار ثابت، retry یا patch روی فایل کتابخانه وجود ندارد؛ frame هنگام بسته‌شدن/خروج cleanup می‌شود.
- خود کنترل ورودی/فلش و footer در مرز «بیرون popup» لحاظ شده‌اند.
- مدیریت گزینه‌ها، انتخاب، Escape و dismissal عادی همچنان از state و مؤلفه‌های React Aria استفاده می‌کند؛ نسخه یا فایل کتابخانه تغییر نکرده است.

کلیدهای `ArrowDown` و تایپ ترتیبی که در دور قبلی برای بازکردن اجباری لیست به تست‌های دسته‌بندی، ساخت برنامه و لیست مربیان اضافه شده بودند حذف شدند. تست‌ها دوباره از کلیک و `fill` عادی استفاده می‌کنند. انتظارهای readiness و assertionهای مفید دیگر دور قبل حفظ شدند.

هشت regression جدید در `frontend/tests/combobox-click.spec.ts` کلیک روی ورودی و فلش، لمس، بازشدن مجدد پس از Escape، حفظ انتخاب، انتخاب با ماوس/کیبورد، toggle فلش و بستن با کلیک بیرون را در عرض‌های ۱۲۸۰ و ۳۹۰ پوشش می‌دهند. تست لمس منتظر opacity و clip-path واقعی می‌ماند، چون popup کتابخانه هنگام آماده‌شدن کیبورد با وجود داشتن کادر DOM، موقتاً نامرئی و clipped است. از `sleep` و `force click` استفاده نشده است.

## نتیجهٔ اعتبارسنجی

- تست‌های هدفمند کنترل‌ها، انتخاب حرکت، ساخت/انتشار برنامه و async picker: **۲۴ پاس، صفر شکست، بدون retry**.
- آزمون کلیک ورودی/فلش در موبایل و دسکتاپ پیش از افزودن تست‌های تکمیلی، سه بار تکرار شد: **۱۳ پاس شامل setup**.
- بیلد تولیدی و TypeScript: پاس.
- lint فرانت‌اند: **۱۶۷ فایل، بدون خطا**.
- Node unit tests: **۱۶ پاس**.
- مجموعهٔ کامل مرورگر: **۱۴۸ پاس، ۱ skip طراحی‌شده، صفر شکست، بدون retry** (۱۴۹ اجرا؛ superuser و PWA فعال).

تست‌ها روی snapshot مستقل از نسخهٔ اصلاح‌شده و دیتابیس تازهٔ `gym_combobox_fix_20261111_test` اجرا شدند. مرورگر و API یک origin محلی داشتند. نسخهٔ اجراشده، تغییرات source همین اصلاح را داشت. backend محصول در این کار تغییر نکرده و suite کامل backend دوباره اجرا نشده است؛ نتایج ۲۱۶ تست گزارش قبلی به‌عنوان اجرای تازهٔ این دور معرفی نمی‌شوند.

## شواهد واقعی حفظ دادهٔ مالی

بکاپ موجود فقط در دیتابیس disposable تازهٔ `gym_finance_backup_audit_20261111_test` restore شد. سپس هم دیتابیس restoreشده و هم `gym_finance_sandbox_v2` در transactionهای صریح **READ ONLY / REPEATABLE READ** خوانده شدند؛ هیچ write یا migration روی دیتابیس اصلی انجام نشد.

مقایسه شامل هر **۱۵ جدول finance**، تمام ردیف‌ها بر اساس شناسه، و **تمام ستون‌های مشترک** بود. JSON هر ردیف canonical شد و SHA-256 مجموعهٔ مرتب ردیف‌ها مقایسه شد:

- هر ۱۵ hash برابر است.
- تعداد ردیف اضافه، حذف‌شده و ردیف موجود با محتوای تغییرکرده، در هر ۱۵ جدول صفر است.
- صرفاً تعداد sale/payment/request مبنای این نتیجه نیست؛ محتوای مشترک قراردادها، snapshotها، تخصیص‌ها، audit و سایر جداول مالی هم مقایسه شده است.
- ستون‌های افزوده‌شده که در بکاپ وجود ندارند، جدا ثبت شده‌اند و ادعای برابری با ستون ناموجود نداریم.
- این نتیجه دربارهٔ داده‌های مالیِ موجود در همین بکاپ است؛ اثبات کامل تغییرناپذیری تمام جداول غیرمالی یا رویدادهای بین دو snapshot نیست.

هش‌ها، شمارش‌ها، ستون‌های جدید و SHA-256 خود فایل بکاپ در [شاهد ساختاریافته](evidence/backup-content-audit.json) قرار دارند. [اسکریپت مقایسه](evidence/audit_finance_backup.py) روش read-only را ثبت می‌کند؛ محتوای ردیف‌ها و اطلاعات ورود کاربران در لاگ خروجی چاپ نشده‌اند.

## تصحیح عبارت migration در گزارش قبلی

شاهد قابل اثبات فعلی این است:

- revision داخل بکاپ: `b8d1e2f3a4c5`.
- revision دیتابیس فعلی: `c3f4a5b6d7e8`.

بنابراین بین ایجاد آن بکاپ و مشاهدهٔ فعلی، schema دیتابیس اصلی ارتقا یافته است. عبارت مطلق «دیتابیس اصلی دست‌نخورده بوده/هیچ migration روی آن انجام نشده» برای کل این بازه دقیق نیست. **محتوای مشترک مالی حفظ شده، اما schema و revision عوض شده‌اند.**

از لاگ‌های ارائه‌شده نمی‌توان زمان و مجری دقیق آن migration را قطعی تعیین کرد یا ثابت کرد در کدام دور اجرا شده است. عبارت «فقط migration جدید روی main اعمال شد» در گزارش قبلی هم ابهام دارد و شاهد زمان‌بندی محسوب نمی‌شود. در این اجرای Codex فقط دیتابیس‌های disposable migrate/restore شدند و اتصال دیتابیس اصلی صریحاً read-only بود.

[نسخهٔ گزارش قبلی پیش از این روشن‌سازی](evidence/second-fix-report-before-clarification.fa.md) حفظ شده است. این سند، تصحیح محدودهٔ ادعاهای آن گزارش است و داده یا لاگ تاریخی را بازنویسی نمی‌کند.
